The gap

Most agent runs go wrong before the first line of code.

Coding agents are good at writing code. They are much worse at deciding what to build, in what order, and how anyone would know it worked. That part is still yours — and a paragraph of intent does not carry it.

1

It picks an architecture you would not have picked. You find out after the third file.

2

It writes task 7 before task 3 — and task 3 was the schema everything else depends on.

3

Nothing says how you would know it worked. So the agent declares success and you go read the diff anyway.

4

You re-explain the same context tomorrow, because it lived in a chat window that is now gone.

How it works

Idea in. Executable backlog out.

Three steps, each one editable before it feeds the next. You are reviewing a document, not babysitting a chat.

STEP 01

Plan

Describe the idea in a sentence. The agent asks focused follow-ups until it stops guessing, then drafts:

  • Summary, audience, value proposition
  • Core features and tech stack
  • Architecture and data flow, as Mermaid diagrams
  • Phased roadmap, estimate, risks
STEP 02

PRD

The approved plan becomes a PRD written the way product teams write one, sized to a first release:

  • Goals and success metrics, target users
  • Scope and release plan, with non-goals
  • Requirements as user stories with acceptance criteria
  • Assumptions, risks and open questions
  • For the coding agent: architecture, data model, tech stack
  • Edit it as a structured view, raw fields, or Markdown
STEP 03

Task board

The PRD splits into atomic coding tasks. Every card carries what an agent needs to execute it:

  • Stable ID, priority, phase
  • Target files and dependencies
  • Instructions and verification steps
  • Run one card, or a whole phase with one button, in dependency order
  • The card moves to Done or Blocked, with the agent's note
  • A verify command per card: Done is marked Verified once it exits 0, or Unverified when nothing checked it
  • Each run starts with what earlier tasks left behind: their notes and the facts agents learned
  • Export AGENTS.md, the plan, the PRD or a handoff bundle: one file, or several as a .zip

Day to day

Built for coming back tomorrow.

A plan is only useful if the next session can pick it up. Undagi keeps the project with the folder, runs the board a phase at a time, and lets you change the plan without losing what is already done.

One folder, one project, any number of chats

A folder holds one project: its plan, PRD, board and memory. Every chat you open in it reads the same board and memory, so tomorrow's chat carries on with the phase left unfinished. Deleting a chat removes its messages; the project stays until you delete it on purpose.

Run a phase, not a prompt

Run Phase 1 runs that phase's To do cards one at a time, each once its dependencies are done, each in its own session with retries and its verify command. The run stops at the first card that does not end Done, so nothing builds on a failure, and you check the phase before the next one starts.

Ask the chat to work on the tasks and it starts the same run, because every chat turn sees the board with its cards, status and dependencies.

Change the plan without losing the work

Syncing the board to a new PRD replaces only cards still in To do. A card that is running or Done keeps its note, its Verified label and its place, and so does any card you added. The new tasks are told which cards stay, so they do not repeat that work. You see how many cards are replaced and kept before anything changes.

See what is left of your plan

The sidebar shows the remaining usage of each subscription you have connected: Claude Code's five-hour and weekly windows, Codex's limits, and Antigravity's per model group. Each is read through that CLI's own usage request, which sends no prompt and spends no quota. A read that fails keeps showing the last one, marked as not refreshed.

Where Undagi is not the right tool.

  • It is a beta, single-user and local: no accounts, no sync, no team features.
  • Packaged installers are for Windows, Linux and Apple Silicon Macs, and none carries a verified publisher signature; on a Mac the first launch needs Open Anyway in Privacy & Security.
  • It plans a new project from an idea. It does not analyse an existing codebase to plan changes to it.
  • No parallel agents, git worktrees or pull-request loop.
  • A card without a verify command counts as Done when the agent says so; it is labelled Unverified.
  • Approvals and path checks are not an OS sandbox. “Full access” means you trust the agent.

Models

Bring your own model. Nothing is bundled.

Undagi ships with no model and no API key. You point it at whatever you already pay for — or at something running on your own machine.

Route by role, not by app

Bind a different connection to each stage, and pick the model for Plan, PRD and Tasks right where you generate them. A strong model drafts the architecture; a cheap, fast one fills in the task board. The app does not care which is which.

Two wire formats, many endpoints

Anthropic Messages and OpenAI-compatible, with presets for local routers, Ollama, LM Studio, OpenRouter, Anthropic, and Gemini. Codex, Claude Code, and Antigravity are detected if you have them installed.

MCP tools, no code changes

Register external tools over stdio or Streamable HTTP. They are discovered lazily and namespaced as mcp__server__tool, isolated from the built-ins. A slow or dead server does not stall the turn — the UI just reports it.

Keys stay where you put them

Keys saved through the UI live server-side in data/undagi.db. Prefer them out of the database? Name an environment variable on the connection instead and keep the value in .env.

Boundaries

It runs on your machine, and it asks first.

File and shell access are real capabilities, so they are gated deliberately rather than enabled by default.

No workspace, no file access

The built-in agent gets no file tools at all until you select a working folder. Paths are then resolved to their real location and checked against that folder, so ../, an absolute path, and a symlink pointing outside are all refused.

Codex, Claude Code and Antigravity bring their own file tools. Without a folder they start in an empty one made for that chat.

Shell is a separate switch

Off by default, and only available once a folder is set. In Ask and Auto mode every command is shown to you and waits for approval before it runs; Full access runs it without asking. Refusing tells the model the command did not run, so it can suggest something else.

Codex and Claude Code ask through the same approval cards, though Claude Code does not ask for what its own settings already allow. Antigravity cannot ask, so it refuses any tool its own settings do not already allow.

A card's verify command is a separate case: Undagi runs it from the board after the agent says the task is done, in your working folder, and asks first unless the chat is on Full access. The shell switch does not govern it, so read the command on the card.

Your data stays local

Sessions, connections, and MCP definitions live in a SQLite file on disk. There is no account, no sync, and no telemetry. Deleting data/ deletes everything. Prompts still go to the model provider you choose; with a local model, nothing leaves your machine.

The server listens on 127.0.0.1 only and refuses requests from other websites.

Permissions come from the project

A project's working folder and shell switch are read from its saved state, never from the request, so a client cannot widen its own access mid-conversation. A chat outside a project may only pick a folder inside a trusted root.

The permission mode you pick per chat only answers approvals. It widens no sandbox.

One thing we will not pretend about.

There is no denylist of dangerous commands. Pattern-matching shell strings does not hold up, and shipping one would imply a protection that is not there. If you enable the shell and approve a command, it runs. Read the approvals.

Install

Download the app, or run two commands.

There is no database to install or run — everything is stored in a single file on disk. Running the install script again keeps your existing data/ and .env.

Desktop app

Installers for Windows (.exe), Linux (.AppImage, .deb) and Apple Silicon Macs (.dmg) are on the v1.0.4-beta release. They bundle their own runtime, so you do not need Node.

None is signed by a verified publisher. On Windows, SmartScreen warns on first run: click “More info”, then “Run anyway”. On a Mac the first launch is refused: open System Settings → Privacy & Security and click Open Anyway, or run xattr -dr com.apple.quarantine /Applications/Undagi.app. There is no Intel Mac build; use the install script below.

LINUX / MACOS

curl -fsSLO https://raw.githubusercontent.com/CharisChakim/undagi/main/install.sh
bash install.sh
undagi
